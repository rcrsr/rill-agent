# Security Policy

The rill agent framework hosts machine-generated rill agents behind HTTP
harnesses that run with host credentials. Request handling, credential and
header propagation, outbound calls made on an agent's behalf, and resource
exhaustion are first-class concerns rather than a subcategory of bugs. This
policy describes what counts as a vulnerability, how to report one, and what to
expect afterwards.

## Supported versions

Only the latest published release of each package is supported. Fixes land
there, and there are no backports to earlier releases.

Reproduce on the current release before reporting. If you cannot upgrade, say so
in the report and give the version you tested.

The packages this policy covers, all published from this repository:

- `@rcrsr/rill-agent` (manifest loader, router, validation)
- `@rcrsr/rill-agent-http` (HTTP harness)
- `@rcrsr/rill-agent-foundry` (Foundry Responses API harness)
- `@rcrsr/rill-agent-chat` (OpenAI-compatible chat harness)
- `@rcrsr/rill-agent-ext-ahi` (agent-to-agent invocation extension)

The rill language runtime, its extensions, the CLI tools, and the config library
are separate repositories with their own policies.

## Reporting a vulnerability

Report privately through GitHub, on the
[Security tab](https://github.com/rcrsr/rill-agent/security/advisories/new) of
this repository. That opens a private advisory visible only to you and the
maintainers.

Do not open a public issue for a vulnerability in a published release.

Include:

- The version you tested, and whether you reproduced it on the current release
- A minimal reproduction: the smallest manifest, request, or agent that shows
  the behaviour
- What a host running the harness loses as a result, stated concretely
- Any host configuration or mounted surface the reproduction depends on

**Do not post working exploit payloads against a live host.** Describe the class
of issue and give a minimal reproduction against a local harness instead.

## What to expect

| Stage | Target |
|-------|--------|
| Acknowledgement | 5 days |
| Initial assessment | 14 days |
| Fix or mitigation plan for a confirmed report | 30 days |

This is maintained by a small team, so these are targets rather than guarantees.
If a report goes quiet past acknowledgement, a nudge on the advisory thread is
welcome.

On a confirmed report, the maintainers publish a GitHub Security Advisory,
release a patched version, and credit you by name or handle unless you ask
otherwise.

## Threat model

A host mounts one of these harnesses and serves rill agents it did not
necessarily write, often generated by a language model. The harness dispatches
requests to the router, which runs the agent with whatever the host mounted.

### In scope

- **Auth bypass.** Reaching an agent, endpoint, or router surface the harness
  was configured to gate, by a different call shape, a renamed route, or an
  unhandled input.
- **Credential or header leakage.** A host credential, bearer token, or internal
  header crossing the harness boundary into a response, a log line, or an
  outbound request it should not reach.
- **Request forgery.** An agent parameter steering an outbound call (including an
  AHI agent-to-agent invocation) to a host or resource the host did not
  authorize.
- **Enforcement bypass.** Any mechanism that validates parameters, filters, or
  gates being defeated by an unlisted default or an unhandled input shape.
  Defaults that fail open are a defect in this class.
- **Resource exhaustion.** A request or agent that wedges or exhausts the host
  process by escaping a documented limit on time, concurrency, or payload size.
- **Supply chain.** Anything in the published package contents or the release
  pipeline that lets a third party alter what consumers install.

### Out of scope

- **A host mounting a destructive capability and an agent calling it.** The
  capability model puts that choice with the host.
- **A request doing something the host authorized but did not intend.** Narrow
  what you mount, or constrain it at the dispatch boundary.
- **Anything requiring the attacker to control the host process or its
  configuration.** That is already full control.
- **Findings from a scanner with no demonstrated impact on a running harness.**

If you are unsure which side a finding falls on, report it. A borderline report
that turns out to be by-design costs less than an unreported bypass.

## Hardening guidance for hosts

The harness's guarantees end at what you mount and how you configure it.

- **Mount the narrowest surface an agent needs.** Every mounted capability is
  authorized by definition, so authorize deliberately.
- **Treat agent-chosen values as untrusted input.** Parameters, mount names, and
  target identifiers come from the agent author. Validate and bind identity to
  the resolved value, not the requested name.
- **Terminate the harness behind your own auth and rate limits.** The harnesses
  do not add authentication of their own; place them behind a gateway that does.
